## Ответы по пунктам запроса

1. **Полнота проверки JWT.** Логика полная: подпись (`algorithms=[settings.ALGORITHM]`,
   только HS256 — `alg:none`/RS-HS confusion отвергаются), срок действия (`exp` в
   `options={"require": ...}` + PyJWT-валидация), обязательные claims `sub/exp/iat/jti/uid/tv`,
   проверка `iat < exp`, `uid == user.id`, `tv == token_version` (глобальный отзыв),
   `jti` в blacklist. **НО** сила подписи не защищена — см. находку A1.
2. **Хеширование паролей.** Безопасно: Argon2id (`Type.ID`, `hash_len=32`, `salt_len=16`,
   параметры ограничены `Field(ge/le)`), bcrypt/legacy — только чтение, при успешном входе
   миграция в Argon2id. **Проблем нет.**
3. **Session Fixation.** Не применимо: серверного session-id нет; при каждом логине минтится
   новый JWT с случайным `jti` (`uuid4`), значение cookie не берётся из ввода клиента. Смена
   пароля инкрементит `token_version` → все прежние токены невалидны. **Проблем нет.**
4. **CORS.** Слишком мягкая по умолчанию — см. находку A3.
5. **OAuth `state`.** OAuth-флоу в проекте нет (нет `/authorize`, `redirect_uri`,
   `authorization_code`, колбэков). Аутентификация — username/password + Subsonic-токен +
   серверный MTProto. **Не применимо.**

## A1 — Critical: `SECRET_KEY` не валидируется (подделка JWT)

`security.py:162,168` подписывает/проверяет JWT ключом `settings.SECRET_KEY`, но в
`core/config.py:38` он объявлен как `SECRET_KEY: str = secrets.token_urlsafe(32)` **без
валидатора**. `music.env.example:19` поставляет `SECRET_KEY=CHANGE_ME`.

- Если оператор оставит плейсхолдер (`CHANGE_ME`) или пустое значение (`SECRET_KEY=`) —
  ключ публично известен/пуст → любой может подделать произвольный токен
  (`sub`, `uid=1`, `tv`) → **полный обход аутентификации и вход под admin**.
- Если переменная не задана — используется случайный ключ на каждый запуск: безопасно
  криптографически, но все токены становятся невалидными после рестарта (и расходятся между
  воркерами).

На старте проверяются только `DATABASE_URL`, `LOG_ARCHIVE_PASSWORD` и связка
`REQUIRE_AUTH/ENVIRONMENT` — `SECRET_KEY` не проверяется.

**Исправление** (`core/config.py`, после `settings = Settings()`):

```python
import secrets as _secrets

_PLACEHOLDERS = {"", "change_me", "changeme", "secret", "secret_key",
                 "your-secret-key", "changethis", "test"}
_MIN_SECRET_BYTES = 32

def _require_strong_secret(value: str | None, name: str) -> str:
    v = (value or "").strip()
    if v.lower() in _PLACEHOLDERS:
        raise RuntimeError(
            f"{name} is unset or still the example placeholder. Generate one with "
            f"`python -c \"import secrets; print(secrets.token_urlsafe(48))\"` "
            f"and set it in music.env."
        )
    if len(v.encode("utf-8")) < _MIN_SECRET_BYTES:
        raise RuntimeError(f"{name} must be at least {_MIN_SECRET_BYTES} bytes.")
    return v

settings.SECRET_KEY = _require_strong_secret(settings.SECRET_KEY, "SECRET_KEY")
```

Рекомендуется также сменить дефолт на `SECRET_KEY: str = ""` (обязательная переменная), чтобы
«забыл задать» падало на старте, а не генерировало эфемерный ключ.

## A2 — High: `SESSION_SECRET` не задан → Telegram-сессии хранятся в открытом виде

`tg/manager.py:33-39`:

```python
def encrypt_session_string(plain_str, secret):
    if not plain_str: return plain_str
    if not secret: return plain_str  # Cannot encrypt without a secret — stored as-is
    ...
```

`SESSION_SECRET` по умолчанию `None` (`config.py:39`) и **не обязателен на старте**. Тогда
`session_string` и `api_hash` Telegram-аккаунтов (полноценные креды аккаунта) пишутся в БД
**в открытом виде**. Утечка БД/бэкапа/чтение через инъекцию → захват Telegram-аккаунта.
Дополнительно: `music.env.example:23` поставляет `SESSION_SECRET=CHANGE_ME`, а ключ Fernet
выводится как `sha256(secret)` (`manager.py:29`) — известный секрет = известный ключ.

**Исправление:** сделать `SESSION_SECRET` обязательным (тот же `_require_strong_secret`, что и
в A1) и убрать plaintext-fallback при записи (сохранив совместимость чтения legacy-plaintext):

```python
def encrypt_session_string(plain_str, secret):
    if not plain_str:
        return plain_str
    if not secret:
        raise TGCredentialError("SESSION_SECRET is required to encrypt Telegram credentials.")
    return _fernet_for_secret(secret).encrypt(plain_str.encode()).decode()
```

Ротацию `SESSION_SECRET` проводить только с перешифровкой (иначе существующие сессии
не расшифруются) — см. [[music.env]].

## A3 — High: CORS по умолчанию разрешает любые приватные origin с credentials

`main.py:367-379`:

```python
allow_origin_regex=(
    r"^https?://(localhost|127\.0\.0\.1|192\.168\.\d+\.\d+|10\.\d+\.\d+\.\d+|172\.(1[6-9]|2\d|3[0-1])\.\d+\.\d+)(:\d+)?$"
    if settings.CORS_ALLOW_LAN else None
),
allow_credentials=True,
```

`CORS_ALLOW_LAN` по умолчанию **True** (`config.py:193`). Итог: любой origin из RFC1918 /
`localhost` допускается с `Access-Control-Allow-Credentials: true`. Cookie сессии —
`SameSite=Lax`, что блокирует классический *кросс-сайтовый* fetch (разные IP = разные сайты),
**но не** защищает случай *один и тот же хост, другой порт* (site игнорирует порт) — например,
страница на `http://<тот же IP>:<другой порт>` или `http://localhost:<другой порт>` читает
ответы API с cookie жертвы. Для интернет-facing сервера такой дефолт нарушает принцип
наименьших привилегий.

**Исправление** (`core/config.py` + `main.py`):

```python
# config.py
CORS_ALLOW_LAN: bool = False   # было True
```

```python
# main.py — не отдавать credentials «широкому» LAN-регэкспу
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.ALLOWED_ORIGINS,          # только явный белый список
    allow_origin_regex=None,
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
    allow_headers=["Content-Type", "Authorization", "X-CSRF-Token", "X-Request-ID"],
    expose_headers=["Content-Range", "Accept-Ranges", "Content-Length", "Content-Disposition"],
)
```

Если LAN-origin реально нужен (мобильный WebView) — вынести конкретный хост в
`ALLOWED_ORIGINS`, а не в регэксп по всему диапазону.
