# Ревью Auth 2026-10-01

#tmusic #security #auth #jwt #cors #audit

## Область

Проверка текущего кода JWT, паролей, выдачи сессий, CORS и OAuth callback/state. Ревью не изменяет рабочий код. Проверки выполняются на синтетических данных без живых PostgreSQL/Telegram и без реальных секретов.

## Ход проверки

- Прочитаны `core/security.py`, `api/dependencies.py`, `services/auth_service.py`, `api/auth_router.py`, схемы паролей, revocation/user cache и CORS middleware.
- Зафиксировано: приложение выдаёт exp/jti/iat/sub, декодер не требует присутствия exp/jti; bcrypt 4.2.1 получает исходные UTF-8 bytes при допускаемых паролях до 128 символов; CORS_ALLOW_LAN=true по умолчанию разрешает private-range origins с credentials.
- OAuth вход/callback в backend/frontend/mobile не обнаружен; React/MediaSession callbacks не являются OAuth.
- Динамические проверки выполнены локально; результаты ниже. Найденные настройки не считать подтверждением конкретной конфигурации рабочего стенда.

## Результаты

### 1. JWT — подпись проверяется, но контракт не полностью строгий

Подтверждено локально: неверная подпись, unsigned/alg=none, истёкший exp, будущие nbf/iat отклоняются. Декодер использует один настроенный алгоритм (HS256 по умолчанию), не доверяет выбору алгоритма из заголовка клиента. Auth dependency проверяет активность пользователя, scope, revocation jti и token_version.

**AUTH-01 — Высокий: uid не проверяется при выборе пользователя.** `api/dependencies.py:100–109` ищет пользователя по sub=username, не сравнивая payload.uid с user.id. Синтетическое воспроизведение: JWT с uid=11/tv=0 принят для новой записи uid=22 с тем же username/tv=0. Если логин удалённого аккаунта повторно выдан другой записи до истечения старого JWT, старый владелец получает её права, в том числе административные. Рекомендация: привязать токен к неизменяемому ID и требовать совпадения uid/sub с записью; не восстанавливать идентичность только по имени.

**AUTH-02 — Неполная валидация claims:** `core/security.py:112` не требует exp/jti/iat, `dependencies.py:97` подставляет пустой jti. Правильно подписанные синтетические JWT без exp и без jti приняты декодером и auth dependency. Это **не обход подписи**: обычная выдача приложения включает эти claims; воспроизведение использовало только тестовый signing key. Рекомендация: require=[sub, exp, iat, jti, uid, tv], проверить типы и непустой jti; при необходимости ввести согласованные issuer/audience одновременно в выдачу и проверку.

### 2. Пароли — bcrypt cost 12, но есть обрезка

**AUTH-03 — Средний:** `core/security.py:34–40` передаёт исходные UTF-8 bytes в bcrypt 4.2.1. Схемы допускают до 128 символов, а bcrypt учитывает только первые 72 байта. Два разных синтетических пароля с одинаковыми первыми 72 байтами и разными суффиксами успешно прошли проверку одного хэша. Рекомендация: перейти на Argon2id с миграцией либо строго ограничить пароль 72 UTF-8 байтами во всех путях установки/проверки (не 72 символами); существующие длинные пароли мигрировать/сбросить согласованно.

Верификатор также поддерживает legacy SECRET_KEY-salted SHA-256 (`security.py:60–79`), после успешного входа выполняется upgrade на bcrypt (`auth_service.py:119–122`). Это не bcrypt-only. Наличие таких хэшей в рабочей БД не проверялось; завершить миграцию перед удалением fallback.

### 3. Session fixation — классическая фиксация не обнаружена

На успешном входе создаётся новый jti/токен и обновляются access_token/CSRF cookies. В локальной проверке jti и CSRF cookie разных выдач различались. От клиента не принимается ID сессии для повторного использования после входа. Cookie имеет HttpOnly/SameSite=Lax; Secure зависит от COOKIE_SECURE (default false). На HTTPS проверить COOKIE_SECURE=true; реальная deployment-конфигурация не загружалась.

### 4. CORS — слишком широкое доверие LAN

**AUTH-04 — Средний:** `main.py:366–376`, `config.py:185`: CORS_ALLOW_LAN=true по умолчанию разрешает любой origin из private IP ranges/loopback с любым портом; allow_credentials=true, allow_headers=[*]. Preflight для неуказанных явно LAN IP и loopback-порта вернул 200 с отражением origin и credentials=true. Неизвестный публичный origin отклонён (400, без allow-origin).

Рекомендация: CORS_ALLOW_LAN=false в production и точный ALLOWED_ORIGINS по scheme/host/port. SameSite=Lax ограничивает передачу cookies между разными sites, но не изолирует разные порты одного site. Локальный preflight-тест не является доказательством кражи cookies в браузере конкретного стенда.

### 5. OAuth state — неприменимо

В проекте не обнаружены OAuth login/callback endpoints, authorization_code/grant_type/redirect_uri flows. LASTFM_SESSION_KEY задаётся конфигурацией, а не получаетcя через OAuth callback приложения. Отсутствующую проверку state не регистрировать как уязвимость отсутствующего flow.

## Оценка перехода на Argon2id (план, не реализовано)

Простая замена hash_password недостаточна. Текущий verify_password направляет любой хэш с префиксом $ в bcrypt; Argon2id будет отклонён. Bootstrap принимает ADMIN_PASSWORD_HASH только с $2, поэтому provisioning Argon2id потребует обновления валидатора. Тесты с прямым ожиданием $2b$ тоже требуют изменения.

Безопасная последовательность:

1. Добавить поддерживаемую pinned зависимость Argon2id. Верификатор должен читать Argon2id, существующий bcrypt и временно legacy salted SHA-256; новые параметры задавать явно и валидировать перед дорогой проверкой.
2. Сначала развернуть поддержку чтения обоих форматов на всех экземплярах, пока новые хэши ещё bcrypt. Затем включить запись Argon2id для новых/изменённых паролей и обновление после успешного входа (check_needs_rehash).
3. Обновить bootstrap/CLI/admin routes, dummy hash и проверки. Не переустанавливать пароль администратора на каждом старте; сохранить one-shot семантику admin_bootstrap_hash.
4. Не пытаться конвертировать готовый bcrypt-хэш в Argon2id без исходного пароля. Неактивные аккаунты остаются на старом формате до входа или согласованного сброса.
5. Учитывать 72-байтную неоднозначность старого bcrypt: суффикс длинного пароля не был сохранён. Для таких случаев предпочтительна явная смена/подтверждение полного нового пароля, а не незаметное закрепление случайно введённого суффикса.
6. Подобрать memory/time/parallelism на целевой машине; выполнить нагрузочные проверки входа/ошибок и ограничить одновременные password checks. Синхронное хеширование сейчас вызывается из async routes и может блокировать event loop; offload должен иметь ограниченную конкуренцию, не неограниченный пул.
7. После появления Argon2id-хэшей откат к текущему bcrypt-only верификатору нарушит вход. Версия для rollback также должна читать оба формата; данные существующих паролей не откатывать массово.

Обычный Argon2id PHC-хэш помещается в password_hash VARCHAR(255), но точную длину выбранного формата подтвердить тестом. API-поля username/password и фронтенд менять не требуется; зависимости/образ пересобрать. Перевычисление хэша того же пароля не требует автоматического сброса JWT; реальная смена пароля должна сохранить bump token_version.

JWT, cookies, Fernet/TG, ключи аудио и выделенные Subsonic-токены не меняют формат от смены алгоритма password hashing. Найденные uid binding / обязательные JWT claims / CORS исправляются отдельно.

Нагрузочные измерения Argon2id и миграция реальной БД не выполнялись. Это план совместимости, не внедрённое решение.

## Проверки и статус

- Проверки JWT подписи/exp/nbf/iat/alg=none, отсутствующих exp/jti, uid mismatch, bcrypt truncation, смены jti/CSRF и CORS preflight выполнены локально на синтетических данных.
- PostgreSQL/Telegram/браузер рабочей среды не использовались; реальные credentials не проверялись и не публиковались.
- Рабочий код Auth **не изменён**; перечисленные findings остаются открытыми.
