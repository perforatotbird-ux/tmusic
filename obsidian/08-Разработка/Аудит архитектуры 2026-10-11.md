# Аудит многоуровневой архитектуры 2026-10-11

#tmusic #architecture #layers #audit

## Область

Слои backend: **Controller** — `app/api/*_router.py`; **Service** — `app/services/*.py`;  
**Repository** — `app/repositories/*.py`; **Model** — `app/models/*.py`.  
Проверялось: бизнес-логика/БД в Controller, прямой доступ к БД из Service, HTTP-логика в Model,  
вызовы через уровень (Controller → Repository / Controller → БД).

## Итог

Архитектура слоёв соблюдается **частично**. Есть один эталонный Service (`search_service.py`) и  
`stream_service.py`/`transcoding_service.py` (через `FileRepository`), но большинство Service и  
Controller работают с БД напрямую, а часть Controller вызывает Repository, минуя Service.

## 3. Model/Entity содержит HTTP-логику — **нарушений нет** ✓

В `app/models/` нет ни `fastapi`, ни `HTTPException`, ни `Depends`/`Request`/`Response`/`status_code`.  
Модели — чистые ORM-сущности (+ свойства вроде `AppUser.is_admin`).

- `app/services/search_service.py` — работает только через `SearchRepository` (эталон слоя Service).

## Вывод и план

1. **Приоритет 1:** вынести доменную логику и запросы из `subsonic_router.py` (62 места) в отдельный  
   `services/subsonic_service.py`; роутер оставить как тонкий адаптер `/rest/*`.
2. **Приоритет 2:** для Service, работающих с БД напрямую (`playlist_service`, `playback_service`,  
   `vfs_import_service`, `admin_service`), ввести репозитории (`PlaylistRepository`,  
   `PlaybackRepository`, …) — по образцу `search_service`/`SearchRepository`.
3. **Приоритет 3:** убрать прямые вызовы Repository из Controller (`vfs_router`, `stream_router`,  
   `admin_catalog_router`) — обернуть в соответствующие Service-методы.
4. `music_library_service.py` — довести до единого стиля (сейчас смешивает репозитории и прямой `db`).

### Шаг 2 (2026-10-11) — вынос read-эндпоинтов из диспетчера в сервис

В `app/services/subsonic_service.py` добавлены функции, роутер теперь только парсит параметры и  
формирует ответ:

- `artist_index(db)` ← `getIndexes`/`getArtists`; `artist_albums(db, artist)` ← `getArtist`;  
  `album_list_entries(db, type_, size)` ← `getAlbumList`/`getAlbumList2`;  
  `album_payload(db, id)` ← `getAlbum`; `album_info(db, id)` ← `getAlbumInfo`.
- `user_playlists(db, user_id)` ← `getPlaylists` (+ убран N+1: count на плейлист → один `GROUP BY`);  
  `playlist_songs(db, pl)` ← `getPlaylist`.
- `playlist_by_id(db, id, user_id, lock)` / `replace_playlist_items(db, pl, ids)` /  
  `playlist_song_count(db, pl)` ← `create/update/deletePlaylist` (запросы и замена треков — в сервисе;  
  транзакция `commit` остаётся в роутере).
- `search_result(db, query, …)` ← `search2`/`search3` (+ артисты альбомов одним `IN`);  
  `similar_songs(db, vf, limit)` ← `getSimilarSongs`; `artist_info_payload(db, artist)` ← `getArtistInfo`.
- `getSong` упрощён до `_file_song(db, vf)`.

Дополнительно вынесены: `album_by_id` / `album_for_track` ← `getCoverArt`, `scrobble`, `getLyrics`;  
`artist_by_name` ← `getArtistInfo`; `user_shares` ← `getShares`; `playlist_by_id` ← `getPlaylist`.

**Шаг 2 завершён:** в `subsonic_router.py` **не осталось ни одного запроса** (`select`/`db.scalar`/  
`db.execute`) — вся работа с БД в `subsonic_service`. В роутере остались только границы транзакций  
(`db.add/commit/refresh/delete`, 7 операций) для `create/deletePlaylist` и формирование ответов.

Эффект: `subsonic_router.py` **964 → 580** строк; запросов в роутере **62 → 0**.
