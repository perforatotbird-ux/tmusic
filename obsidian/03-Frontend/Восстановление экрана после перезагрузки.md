# Экран переживает перезагрузку — «где я был»

#tmusic #frontend #navigation

Связано: [[Обзор Frontend]] · [[Структура UI]] · [[Zustand stores]] · [[Чеклист разработки]] · [[00-Главная]]

---

## Проблема (2026-10-29)

В приложении **нет роутера**: всё «где я нахожусь» — это состояние компонента
`MusicLibrary` (`mobileTab`, `activeKind`, `selectedArtist`, `showAdmin`, `libSection`)
плюс позиция скролла. Поэтому любая перезагрузка — F5 в браузере, reload WebView в
Android-оболочке, возврат задачи в PWA — сбрасывала пользователя на главную
(«Медиатека» → «Исполнители»), а глубоко прокрученный каталог — в начало списка.

## Решение

`frontend/src/utils/viewPersistence.js` — снимок экрана в **`sessionStorage`**
(ключ `tmusic_view_state_v1`) и позиция скролла (ключ `tmusic_scroll_v1`).

`sessionStorage`, а не `localStorage`, выбран сознательно: снимок принадлежит
текущей вкладке/сессии. Новая вкладка и новый запуск приложения по-прежнему
стартуют с главной — как и ожидается от плеера.

### Что хранится

| Поле | Смысл |
|------|-------|
| `mobileTab` | нижняя навигация: `library` / `artists` / `albums` / `profile` |
| `activeKind` | раздел каталога (`artist`, `albums`, `compilation`, `favorites`, `cached`, …) |
| `libSection` | встроенная панель из меню профиля (`recent`) |
| `search` | фильтр каталога |
| `showAdmin` | открыта ли админка |
| `artistId` | открытая карточка артиста |
| `album` + `albumArtist` | открытая шторка треклиста (`AlbumDetail`) |
| `adminTab` | вкладка админки (`overview` … `analytics`) |
| `searchOpen` + `searchQuery` | открытое окно поиска и его запрос |
| `playerExpanded` | развёрнутый полноэкранный плеер |

### Что НЕ восстанавливается

| Случай | Почему |
|--------|--------|
| Дерево «Папки» (`FolderBrowser`) | раскрытые узлы — набор `Set` в дочернем компоненте, восстановление потребовало бы N запросов `vfs/children` при старте |
| Окно «Плейлисты» (`PlaylistsModal`) | модальный редактор, открывается одним тапом из меню |
| Карточка из «В кэше» | у неё нет каталожной строки: `artistId` пишется только для числовых id |
| Шторка кэшированного/«Любимых» альбома | треклист живёт на устройстве, `folder_id` нет — такой альбом отбрасывается при валидации |
| Глубина пагинации («Показать ещё») | страницы каталога не запрашиваются заново; скролл упирается в текущий низ списка |

## Как работает восстановление

1. `MusicLibrary` читает снимок **синхронно в первом рендере**
   (`useState(() => readViewState(...))`) и инициализирует им `mobileTab`,
   `activeKind`, `libSection`, `search`, `showAdmin`. Поэтому первый же запрос
   каталога уходит за нужным разделом — промежуточной отрисовки главной нет.
2. Снимок применяется **один раз и только после проверки сессии**
   (`viewRestoredRef`): карточка артиста требует авторизованного
   `getArtistDetail`, а админка не должна открываться у того, кто перестал быть
   админом (`showAdmin && !isAdmin` → сброс).
3. Удалённого артиста восстановление не педалирует: 404 → тихий возврат в
   каталог, без красного алерта.
4. Обратная запись начинается **после** восстановления — иначе первый рендер
   затёр бы снимок значениями по умолчанию.
5. Выход из аккаунта вызывает `clearViewState()`: следующий вход начинается с
   главной, чужой экран не «протекает».

### Скролл

Браузер восстанавливает позицию сам, но слишком рано — каталог грузится
асинхронно, документ ещё короткий, и позиция сбрасывается в 0. Поэтому
`history.scrollRestoration = 'manual'`, а позицию возвращает `restoreScrollY()`:
он опрашивает `scrollHeight` в `requestAnimationFrame`, пока документ не дорастёт
до цели (не дольше 4 с), иначе упирается в текущий низ. Ручной скролл, `touchstart`
или нажатие клавиши отменяют восстановление, чтобы страницу не выдёргивало
из-под пользователя.

Позиция пишется на `scroll` (троттлинг 250 мс — `sessionStorage.setItem`
синхронный) и принудительно на `pagehide`. Пока открыта шторка треклиста, `body`
зафиксирован (`position: fixed` из `useBodyScrollLock`), `window.scrollY` врёт
нулём — такая запись пропускается, а восстановление откладывается до закрытия
шторки.

## Безопасность

Снимок — это пользовательский ввод, который переживает перезагрузку (XSS,
расширение, оборванная запись). `readViewState()` не доверяет ничему: белые
списки табов/разделов/вкладок админки передаёт вызывающий код, id приводятся к
положительным целым, строки обрезаются и чистятся от управляющих символов,
карточка альбома сводится к известным скалярам (`id`, `folder_id`, `title`,
`artist_id`, `kind`, `track_count`, `year`, обложки) — посторонние поля в
хранилище не попадают. Любая ошибка хранилища (приватный режим, квота) глушится:
восстановление экрана — удобство, а не условие работы.

  «Медиатека» и чистый снимок; новая вкладка начинает с главной.

## Ограничения

- `history.scrollRestoration = 'manual'` действует на всё приложение: кнопки
  «назад/вперёд» браузера позицию не восстанавливают (в приложении и нет
  history-записей — переходы не создают их).
- Если каталог за время перезагрузки заметно уменьшился, скролл упрётся в низ
  списка — это ожидаемо, пользователь остаётся в том же разделе.
- Снимок живёт до закрытия вкладки. Для «продолжить с того же места после
  перезапуска приложения» понадобился бы `localStorage` и отдельное решение
  владельца.
