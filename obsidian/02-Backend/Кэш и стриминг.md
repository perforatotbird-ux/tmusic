## Уровни кэширования

| Уровень | Где | ТTL / лимит | Назначение |
|---------|-----|-------------|------------|
| **RAM audio** | `ram_cache_service` | LRU: 15 треков / **512 МБ** | Повтор play без TG round-trip |
| **Pre-cache (UI)** | `playerStore` + browser `fetch` | 2×2 МБ + 512 КБ «хвост», по shuffle-порядку | Упреждающая загрузка; принимается только HTTP 206 |
| **Covers disk** | `cache/music_images` (`{key}.bin` + `{key}.meta`), custom — `cache/music_covers` | **TTL=0** (перманентно) | Показ артистов/альбомов — всегда из локального кеша по `?key=`; remote fetch только один раз при обогащении или явном `?url=` (см. [[API Library]]) |
| **Cover HTTP cache** | headers | ETag + cache-control (`utils/http.py`) | 304 на повторы |
| **External provider disk** | `core/disk_cache` (`cache/external/`) | lyrics 90 дн / lastfm 14 дн / negative 15 мин | Не долбить LRCLIB и Last.fm |
| **Клиентский API-cache** | `src/api/cache.js` | catalog 5м · stats 10м · tracks/vfs 2м + single-flight | Убрать дубли запросов грида/плеера |
| **Cover presence** | `services/coverMissing.js` (Set) | до bust мутацией | Не переспрашивать `/covers/manifest` |
| **SW shell/covers** | `public/sw.js` | cache-first `/assets/*` (cap 24) · covers LRU 120 | Офлайн-шелл, мгновенные обложки |
| **Player localStorage** | `tmusic_session` / `tmusic_durations` | session-live / cap 400 | F5 не сбрасывает очередь; длительности |
| **Transcode disk** | `cache/music_transcoded` | `TRANSCODE_CACHE_MAX_BYTES` (LRU) | MP3 320k; дисковый I/O и ffprobe вынесены в `asyncio.to_thread` |
| **Mobile Offline Cache (Telegram-style)** | IndexedDB `tmusic_offline_cache` | Настраиваемый (3-30 дней / 500 МБ - 10 ГБ) | Офлайн-воспроизведение треков без интернета ([[Кэширование и офлайн]]) |

## Внешний disk-cache (LRCLIB / Last.fm)

Модуль `backend/app/core/disk_cache.py` — общий JSON-кеш на диске для «тяжёлых» внешних ответов.

| Свойство | Реализация |
|----------|-----------|
| Ключ | `sha256(namespace + canonically-serialized payload)[:32]`, payload — разрешённая идентичность (casefold для lastfm, parse_track_meta для lyrics) |
| Namespaces | `lyrics` (90 дн, 20 МБ/5000), `lastfm` (14 дн, 5 МБ/5000) — изолированы, бюджеты per-namespace |
| Негативный кеш | `value=null` живёт `NEGATIVE_TTL_SEC` (15 мин) — трек без текста не вызывает LRCLIB дважды при каждом открытии |
| Eviction | по mtime файла; hit продлевает «свежесть» доступа → LRU без памяти процесса |
| Запись | атомарно `.tmp` → `os.replace`; битый JSON читается как miss |
| Интеграция | `lyrics_service._lookup_upstream` / `lastfm_service._fetch_*` — сеть; публичные `get_lyrics`/`get_artist_info`/`get_track_info` — кеш-обёртки |
| Admin | `GET /api/admin/cache/stats`, `POST /api/admin/cache/flush?kind=external|ram|all&namespace=` (с аудит-логированием) |

Тесты: `tests/test_disk_cache.py` (11 шт) + автофикстура `conftest.py`, перенаправляющая `external_cache.root` в tmp на каждый тест (иначе негативные записи перетекают между запусками и глушат сетевые стабы).

## Клиентский кеш API (single-flight)

`frontend/src/api/cache.js` — общий слой для `library.js`, `stream.js`, `vfs.js`:

- `memoize(key, ttl, fetcher)` — параллельные вызовы одного URL ждут **один** запрос; свежий ответ не идёт в сеть;
- `bustMediaCaches()` — сбрасывает `/api/library`, `/api/stream`, `/api/vfs` одним контрактом;
- `bustCatalogCache()` (экспорт из `library.js`) = `bustMediaCaches()` + `resetCoverProbes()` — единственная точка инвалидации для всех мутаций каталога, rename, cover-ops и VFS-импорта (событие `tmusic:vfs-imported`).

## RAM Cache (DoS-защита)

Конфиг:
- `RAM_CACHE_MAX_ITEMS` (default 15)
- `RAM_CACHE_MAX_BYTES` (default 512 * 1024 * 1024)

LRU вытесняет старые треки при превышении **любого** из лимитов. Защита от OOM через забивание кэша.

## Range + AES-256-GCM

1. Клиент шлёт `Range: bytes=a-b`
2. `stream_service.get_track_size` возвращает известный **plaintext** size; encrypted card без разрешённого header получает `size=null`. Перед HTTP response `get_plain_track_size` читает реальный header/block_size либо использует полный RAM payload; неизвестный размер не заменяется оценкой по default block size.
3. Блоки расшифровываются on-the-fly (`decryption_service`) при `vfile.is_encrypted`
4. Ответ **206** с корректным `Content-Range`

Ключи vault:
- `ENCRYPTION_RECOVERY_KEY` (primary)
- `ENCRYPTION_FALLBACK_KEYS` (legacy tracks)

См. [[music.env]] · [[Архитектура]]

## Auth для `<audio>`

HTML5 `<audio>` не шлёт Authorization. Same-origin cookie-сессия принимается backend для основного URL. Для клиентов без cookie:
1. SPA вызывает `POST /api/stream/token` → short-lived JWT
2. `audio.src = /api/stream/{id}?token=...`
3. query-путь принимает только `scope=stream`; session JWT в URL запрещён

См. [[API Stream]] · [[ADR-004 Cookie Auth CSRF]]

[[Ревью ресурсов 2026-10-01]]: in-flight buffers encrypted audio имеют отдельный общий RAM_CACHE_MAX_BYTES бюджет; резерв 2×plaintext покрывает buffer и копию. ## Длинные M4A: подготовка перед воспроизведением (2026-10-08)

Web-player ждёт `ready` через отменяемый опрос каждые 2 секунды. Ошибка декодирования не завершает трек и не переводит очередь дальше. Смена трека/reset/пауза отменяют ожидание; старый ответ не запускает предыдущий трек. Для MP3-подготовки используется отдельный URL `?representation=mp3`: отсутствие результата даёт 409, raw M4A не подставляется. Заголовок `no-store` не позволяет переиспользовать прежнее raw-представление.

Исходник скачивается/расшифровывается порциями в seekable temp-файл. FFmpeg пишет `.part.mp3` на диск; после проверки размера файл атомарно переименовывается, manifest публикуется до READY. Отмена дочернего процесса завершает его до удаления temp-файлов. `TRANSCODE_DOWNLOAD_TIMEOUT_SEC` и `TRANSCODE_TIMEOUT_SEC` — по 1800 секунд, отдельно для скачивания и конвертации. Текущий результат защищён от немедленного вытеснения; одиночный файл может временно превысить лимит кэша. Linux Docker устанавливает системный FFmpeg и использует `/usr/bin`.

Новые офлайн-копии трансформируемых форматов скачиваются после подготовки; legacy Blob при ошибке онлайн переключается на серверный путь. Native Android и реальный Telegram требуют отдельного smoke-теста. Код изменён локально, проверки и публикация ещё не завершены; live deployment не выполнялся.

Новые тесты ожидания, A→B→A, отмены, retry и online/offline Blob проходят. Production frontend build проходит. Дополнительные smoke и итоговый прогон ещё выполняются.

### Итоговые проверки перед PR

- 48 изолированных backend tests — passed (синтетические источники/SQLite, недоступный тестовый PostgreSQL URL; рабочая БД и `music.env` не использовались).
- Frontend: 149 tests, 143 passed / те же 6 baseline failures; 12 новых тестов проходят. Старые ошибки не исправлялись в рамках этого PR.
- Production build, `node --check`, `compileall`, `git diff --check` — passed.
- Реальный FFmpeg smoke: синтетический 30-минутный M4A с обычным расположением MP4 metadata → MP3, ffprobe duration 1800.05 s, 72 003 015 bytes, READY; temp-файлы удалены. Это функциональная проверка, не бенчмарк VPS.
- Изолированный Chromium harness с реальным `<audio>` и mocked API: pending не запрашивает raw M4A, ручное переключение сохраняется, поздний ответ старого трека не подменяет текущий, подготовленный MP3 декодируется без page errors.
- Живой Telegram, реальные проблемные файлы, Firefox, Android и сборка Docker-образа ещё требуют smoke после применения. Слияние/деплой, смена секретов, пароля администратора и изменение рабочей БД не выполнялись.

Для обновления web-версии нужна пересборка frontend (`npm ci && npm run build` в `frontend`) и перезапуск backend; при Docker — пересборка образа. Важно не удалять DB volumes или `music.env`. На диске нужен запас под исходник + временный MP3 каждого воркера; RAM теперь не содержит целые входной/выходной аудиофайлы этого pipeline.
