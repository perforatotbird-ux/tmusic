# Производительность админки

#tmusic #backend #performance

Разбор жалобы владельца (2026-10-12): «админка открывается с тормозами».

---

## Измерения (живая БД: 276 артистов, 4431 альбом, 88 276 треков, 81 МБ, PostgreSQL 18.1)

| Эндпоинт | До | После |
|----------|----|-------|
| `GET /api/admin/overview` (холодный) | 1.53 с | ~1.07 с |
| `GET /api/admin/overview` (тёплый) | 0.56–0.68 с | **0.32 с** |
| `GET /api/admin/system/health` | 0.55 с | **0.018 с** |
| `/overview` + `/system/health` подряд | ~1.1 с | **0.35 с** |
| `GET /api/admin/db/stats` | 0.68–0.83 с | 0.44 с |

Для сравнения (не были узким местом): `/backups` 0.009 с, `/users` 0.005 с,
`/audit` 0.016 с, `/analytics` 0.037 с, `/catalog/artists?limit=500` 0.039 с.

---

## Корневая причина №1 — `pg_database_size()` вычислялся дважды

`DbStatsRepository.overview()` отдаёт и `db_size` (`pg_size_pretty(...)`), и
`db_size_bytes` (сырое значение) — это были **два отдельных SQL-запроса**.
`pg_database_size()` обходит все отношения БД: **0.265 с** на этой базе. Итого
0.53 с из 0.56 с на каждый вызов, и метод вызывается несколько раз за открытие
панели.

Исправление (`app/repositories/db_stats_repository.py`): один запрос с
`MATERIALIZED` CTE — значение считается ровно один раз, pretty-форма
выводится из него же.

```sql
WITH s AS MATERIALIZED (SELECT pg_database_size(current_database()) AS b)
SELECT b AS db_size_bytes, pg_size_pretty(b) AS db_size FROM s
```

## Корневая причина №2 — один и тот же блок данных запрашивался 3 раза

Открытие панели дёргает `/overview` **и** `/system/health` (а вкладка «БД» —
ещё и `/db/stats`); каждый вызов заново считал `db_overview`.

Исправление (`app/services/admin_service.py`): TTL-мемо на 10 с
(`_DB_OVERVIEW_TTL_SECONDS`, `_db_overview_cache`). Политика кеширования — в
сервисе, SQL остаётся в репозитории (ADR-001). Каждому вызывающему отдаётся
`dict(payload)`, чтобы запросы не делили один мутабельный объект.

Инвалидация — `invalidate_db_overview()` из `run_vacuum()`, `run_analyze()`,
`run_reindex()` и после успешного `restore_backup()`.

> Дашборд — поверхность мониторинга, а не журнал операций: счётчик соединений
> 10-секундной давности безвреден, а холодное открытие — нет.

---

## Что осталось (не сделано намеренно)

- `_library_counts()` в `admin_router.py` — 8 отдельных `count(*)`. Суммарно
  ≈0.03 с, на фоне исправленного оверхеда не окупает переписывания.
- `/db/stats` ≈0.44 с — почти всё время в `table_stats()`
  (`pg_stat_user_tables` + `pg_total_relation_size` на строку). Это отдельная
  вкладка, не участвует в открытии панели. Если понадобится — кешировать тем
  же приёмом.

## Тесты

`backend/tests/test_admin_perf.py`:
- `pg_database_size` встречается ровно в одном statement за вызов
  (`before_cursor_execute` listener);
- `db_size` и `db_size_bytes` согласованы;
- сервис мемоизирует (второй вызов не идёт в репозиторий), отдаёт разные
  объекты и реагирует на `invalidate_db_overview()`.
