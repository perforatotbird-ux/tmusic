# Сканирование каталога (Last.fm)

#tmusic #backend #metadata

Разбор жалобы владельца (2026-10-12): «В админке есть функция Сканировать — она
ничего не выполняет, а должна обновлять обложки и инфо для выбранного артиста.
Должен быть всплывающий в левом верхнем углу Progress bar со статусом получения
обложек».

Кнопка **работала**, но её результат был неотличим от мёртвого контрола: два
бага в слое Last.fm затирали полезные данные placeholder-ами, а ответ ничего
не сообщал. К этому добавилась вторая половина жалобы — скан висел на одном
блокирующем запросе десятки секунд, и админ видел только неактивную кнопку.
Разобрано по частям.

---

## 1. Корневая причина: `artist.getInfo` больше не отдаёт обложки артистов

Last.fm убрал артист-изображения из API: **для любого артиста и любого размера**
возвращается один и тот же ассет «звезда» с маркером
`2a96cbd8b46e442fc41c2b86b821562f`.

Старый код брал `next(img["#text"] for img in images)` — то есть **первый**
элемент массива, а это 34-пиксельная миниатюра того же placeholder-а. Последствия:

- обложка артиста записывалась в БД, хотя реального изображения не существует;
- ключ дискового кеша — детерминированный SHA-1 от `scheme://netloc/path`
  (`cover_cache.url_to_key`), а URL у всех один → **все просканированные артисты
  схлопывались в одну картинку**;
- при этом затиралось настоящее artwork, уже проставленное другими импортёрами.

Аналогично вики-саммари: если вики у артиста нет, Last.fm отдаёт строку, целиком
состоящую из ссылки «Read more on Last.fm» — она сохранялась как биография.

### Защита в `app/services/lastfm_service.py`

| Функция | Что делает |
|---------|-----------|
| `is_placeholder_image(url)` | `True` для placeholder-а и для пустых значений |
| `pick_image(images)` | самый крупный **не-placeholder** URL по `_IMAGE_SIZE_RANK` (`mega` 5 … `small` 1), иначе `None` |
| `clean_bio(summary)` | срезает хвост «Read more on Last.fm»; если остался только стаб → `""` |
| `_sanitize_cached(info)` | повторно применяет оба guard-а **на чтении из кеша** |

`_sanitize_cached` — ключевая деталь: кеш Last.fm живёт 14 дней и переживает
рестарт, поэтому записи, сделанные до появления фильтра, продолжали бы
инжектить placeholder и стаб в каталог. Фильтрация на чтении закрывает это без
инвалидации кеша.

Также добавлен `get_album_info(artist, album, force=False)` / `_fetch_album_info`.
Album artwork на Last.fm **осталось настоящим** — это и есть рабочий источник
обложки для артиста, у которого своей нет. Промах приходит как HTTP 404 с телом
`{"message": "Album not found", "error": 6}` — `_request` теперь ловит `HTTPError`
и логирует такие ответы на уровне `debug` (скан спрашивает десятки альбомов,
`warning` на каждый промах хоронил реальные проблемы).

Все три геттера (`get_artist_info`, `get_track_info`, `get_album_info`) получили
`force: bool = False`. `force=True` пропускает кеш и перезаписывает его: явное
«Сканировать» должно отражать Last.fm **сейчас**, а не снимок двухнедельной
давности.

## 2. Эндпоинт `POST /api/admin/catalog/artists/{id}/scan`

Переписан: сначала была одна блокирующая ручка, теперь это **фоновая задача**
(`app/services/scan_service.py`, см. §4). Сама логика — та же:

1. `get_artist_info(display_name, force=True)`;
2. био/MBID пишутся **только если реально отличаются** (собирается список
   `fields`); пустая строка и стаб — не данные;
3. по альбомам артиста (`list_artist_albums`, не больше `MAX_ALBUMS_PER_SCAN = 12`
   запросов к Last.fm): пропускаются альбомы с `custom_image_key` (ручная обложка
   неприкосновенна) и с уже настоящей `cover_url`; для остальных берётся
   `get_album_info(..., force=True)`, найденная обложка прогревается в дисковый кеш;
4. обложка артиста = `provider_image or album_cover`, и **перезаписывается только
   если текущей нет или она сама placeholder**. Ничего не понижается в качестве;
5. `image_source` ∈ `lastfm | album | existing | None` — откуда взялась картинка;
6. при изменениях ставится `locked = True` (явное сканирование — это курирование,
   авто-энричмент не должен потом переписывать формулировки), `enriched_at`,
   `updated_at`, `commit`;
7. если обложка взята от Last.fm — прогрев кеша, иначе карточка отдаст 404.

Ответ задачи (в `report`): `{ok, id, display_name, updated, fields,
albums_scanned, albums_updated, albums_total, image_source, bio, image_url,
mbid, tags, similar}`.

`POST /api/admin/catalog/albums/{id}/scan` переписан так же: сначала
`album.getInfo`, при промахе — `track.getInfo` по первому треку альбома
(единственный путь, когда у релиза нет записи в Last.fm). `cover_url` не
затирается, если у альбома есть `custom_image_key`.

## 3. UI: сканирование перестало быть «немым»

`frontend/src/utils/scanReport.js` — `describeScan(report)` собирает одну строку
фидбека: `Обновлено: био · MBID · обложка`, `обложки альбомов: N`,
пометка `(обложка взята из альбома)`. Пустой отчёт даёт явное «Last.fm не отдал
новых данных — изменений нет.» вместо тишины.

### Всплывающий Progress bar в левом верхнем углу

Вторая половина жалобы: «должен быть всплывающий в левом верхнем углу Progress
bar со статусом получения обложек». Реализация:

| Файл | Роль |
|------|------|
| `frontend/src/store/scanStore.js` | единственное место, которое стартует скан, опрашивает задачу и хранит снапшот |
| `frontend/src/components/ScanProgressHost.jsx` | сам бар: `position: fixed`, `left: max(12px, var(--safe-left))`, `top: calc(12px + var(--safe-top) + var(--offline-banner-h, 0px))`, `z-index: var(--z-scan) = 9300` (выше плеера/навигации, ниже модалок) |
| `frontend/src/utils/scanProgress.js` | `percentOf` / `scanCounter` / `SCAN_STAGE_LABEL` — арифметика отдельно от JSX, чтобы её можно было тестировать |
| `frontend/src/index.css` | `.tmusic-scan-card`, `.tmusic-scan-indeterminate`, `--z-scan`, `@keyframes tmusic-scan-slide`, `prefers-reduced-motion` |

Свойства, которые делают его честным индикатором, а не декорацией:

- **этап и счётчик обложек** — `Обложка альбома «Nevermind»…` + `3 / 8`; счётчик
  берётся из `progress.current/total`, а `total` считается **до** начала работы
  (список альбомов формируется заранее), поэтому бар действительно доходит до
  100 %, а не застревает;
- **неопределённая стадия** — на этапе запроса данных артиста `total` ещё
  неизвестен: рисуется бегущая полоска (`tmusic-scan-indeterminate`), а не
  сфабрикованные «0 %» или «100 %»;
- **доступность** — `role="progressbar"` с `aria-valuenow/valuetext`, обёртка
  карточки `role="status"` + `aria-live="polite"`;
- **не перехватывает клики** — у хоста `pointer-events: none`, только у карточек
  `auto`;
- **финальный отчёт** — по завершении в карточке появляется строка
  `describeScan(report)`; при ошибке — `job.error` красным;
- **живёт на уровне App**, поэтому бар не исчезает, если админ ушёл с экрана
  админки во время скана.

`AdminCatalog.jsx`: `scanArtist` теперь вызывает
`useScanStore.getState().startArtistScan(...)` — то есть **только стартует**
задачу. Дальше всё показывает бар. Список артистов/альбомов перечитывается через
событие `tmusic:catalog-changed`, которое стор рассылает при завершении задачи
(фоновая задача не может позвать callback компонента).

## 4. Скан как фоновая задача: `app/services/scan_service.py`

Почему: скан — это до `MAX_ALBUMS_PER_SCAN = 12` запросов к Last.fm, то есть
десятки секунд. Пока это был один блокирующий запрос, админ видел кнопку без
счётчика, этапа и ошибки — отсюда и «она ничего не выполняет». Логика вынесена
из роутера в сервис (ADR-001: в `app/api` нет god objects).

| Элемент | Назначение |
|---------|------------|
| `ScanJob` (dataclass) | `job_id, artist_id, display_name, actor_id, status ∈ running\|completed\|failed, error, report, progress{current,total,stage,message}` |
| `_JOBS` / `_TASKS` / `_BY_ARTIST` | реестр задач; `_TASKS` держит **сильную** ссылку на `asyncio.Task`, иначе её может собрать GC посередине работы |
| `_reap()` | удаляет завершённые задачи старше `JOB_TTL_SEC = 600` |
| `get_job(job_id, actor_id)` | задача видна **только своему** актору |
| `start_artist_scan(...)` | регистрирует задачу и запускает `asyncio.create_task(_run(job))`; под `_JOBS_LOCK` |
| `scan_artist_in_db(db, artist_id, report)` | вся бизнес-логика скана; `report(stage, message, current, total)` — колбэк прогресса |
| `_fetch_album_cover(artist, album)` | обложка альбома с Last.fm + прогрев кеша; best-effort, скан не падает из-за сбоя хоста |

Исключения несут HTTP-статус, чтобы роутер оставался тонким:
`ScanBusy(409)`, `ScanNotFound(404)`, `ScanUnavailable(503)`.

### Контракт эндпоинтов

| Метод | Путь | Поведение |
|-------|------|-----------|
| `POST` | `/api/admin/catalog/artists/{artist_id}/scan` | `200` + `{accepted: true, job_id, status: "running", progress: …}` — **сразу**, без результата скана. `404` нет артиста · `409` уже сканируется / больше `MAX_CONCURRENT_SCANS = 3` · `503` Last.fm не сконфигурирован |
| `GET` | `/api/admin/catalog/scan/{job_id}` | снапшот `{job_id, artist_id, display_name, status, error, report, progress}`; `404` чужая или несуществующая задача |

Обе ручки — `async def`: `start_artist_scan` вызывает `asyncio.create_task`, а
sync-def в FastAPI уходит в threadpool, где **нет работающего event loop**.

Этапы прогресса: `artist` → `albums` (по одному шагу на альбом) → `save` →
`done`. При `updated: false` финальное сообщение — «Новых данных у Last.fm нет».

## Живая проверка (артист #146 «Кино», с восстановлением)

| Прогон | Результат |
|--------|-----------|
| 1-й | `updated: true`, `fields: ['bio']`, `albums_scanned: 3`, `albums_updated: 0`, `albums_total: 48`, `image_source: 'existing'` |
| 2-й | `updated: false`, `fields: []`, `albums_updated: 0` — идемпотентно |

Ни placeholder, ни стаб в БД не записаны. Оставшийся «пробел» честный: у
выборочных артистов без обложек (квартирники «Кино», DJ HUKAR и т. п.) на
Last.fm **действительно нет artwork** — скан сообщает `albums_updated: 0`, а не
пишет молча звезду (прежнее поведение).

## Разовый ремонт уже испорченных строк

Guard-ы закрывают будущие сканы, но 77 артистов уже несли placeholder в
`music_artists.image_url` (два варианта URL одного и того же ассета). Для них —
`scripts/repair_placeholder_covers.py`:

```
python scripts/repair_placeholder_covers.py                 # только план
python scripts/repair_placeholder_covers.py --apply
```

Порядок действий для каждого артиста:
1. если у него есть альбом с настоящей обложкой — берётся она, **без сети**;
2. иначе до `--albums-per-artist` (по умолчанию 4) запросов `album.getInfo`;
3. если настоящей картинки нет нигде — `image_url` **обнуляется**, и карточка
   показывает штатный плейсхолдер приложения вместо общей «звезды».

Ничего не понижается: артист с настоящей обложкой не трогается, а при
`custom_image_key` ручная обложка продолжает выигрывать при отображении.
Перед первой записью в `cache/placeholder_cover_backup-<timestamp>.json`
складывается бэкап всех изменяемых значений — откат тривиален. Скрипт
идемпотентен.

**Выполнено 2026-10-12:** 77 строк → 39 из альбома, 1 из Last.fm
(Alice Cooper), 37 обнулены. Проверка после: сохранённых placeholder-ов у
артистов **0** (было 77), у альбомов 0; карточки отдают разные
`/api/library/cover?key=…` вместо одного общего ключа.

> Ловушка при написании подобных скриптов: `is_placeholder_image(None)` возвращает
> `True` (это верно для решения об отображении), поэтому селектор «испорченных»
> строк обязан требовать непустое значение — иначе скрипт на каждом прогоне
> заново «находит» только что обнулённые строки.
