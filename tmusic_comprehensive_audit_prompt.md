# Промт: всесторонний аудит T‑Music

## 1. Роль и цель

Ты работаешь как независимая команда уровня Principal Engineer, AppSec/DevSecOps Engineer, Performance Engineer, QA Lead и UX/UI Accessibility Reviewer. Проведи **всесторонний аудит текущего состояния T‑Music**: качество кода и архитектуры, корректность бизнес-логики, производительность, безопасность, UI/UX, доступность, мобильный опыт, тестируемость и готовность к эксплуатации.

Цель — не перечислить потенциальные проблемы по чек-листу, а установить, какие дефекты **действительно присутствуют в текущей версии кода**, насколько они опасны, как их воспроизвести и какие изменения нужны для исправления.

Работай по фактически доступному репозиторию и его текущему состоянию. Если исходный код или часть окружения недоступны, прямо укажи ограничение и не делай вид, что проверка выполнена.

## 2. Контекст проекта

Документация Obsidian описывает T‑Music как self-hosted музыкальный сервер поверх Telegram Cloud. Используй это как исходную гипотезу, но проверяй по коду, lock-файлам, конфигурации и тестам: документация может отставать от реализации.

Ожидаемые подсистемы:

- **Backend:** Python, FastAPI, SQLAlchemy, PostgreSQL; слои API/router → service → repository → models; конфигурация из `music.env`.
- **Telegram:** Pyrogram/MTProto, кластер master/slave, in-memory sessions, failover и `FloodWait`.
- **Стриминг:** HTTP Range/206, выдача аудио из Telegram, RAM LRU-кэш, pre-cache следующих треков, транскодирование в MP3, дисковый кэш транскодинга, при необходимости AES-GCM для legacy-зашифрованного аудио.
- **Backend-функции:** VFS (`folders`, `vfiles`, `folder_closures`), каталог артистов/альбомов, обложки, playlists, favorites, history/resume, public shares, Subsonic API, аналитика, админка, импорт VFS из PostgreSQL SQL dump.
- **Frontend:** React, Vite, Zustand; библиотека, плеер, поиск, админка, модальные окна, PWA/Media Session, клиентское API-кэширование.
- **Mobile/offline:** Capacitor/Android WebView, IndexedDB-кэш аудио и обложек, офлайн-режим, нативная MediaSession/foreground service.
- **Инфраструктура:** Docker/Compose, PostgreSQL, скрипты запуска и обслуживания.

Принцип архитектуры из ADR: **тонкие HTTP-роутеры, бизнес-логика в services, доступ к данным через repositories; избегать God Objects**. Не считай наличие соответствующего документа доказательством соблюдения принципа.

## 3. Правила аудита и безопасной работы

1. **Сначала аудит, потом исправления.** Не меняй прикладной код, конфиги, миграции, зависимости и данные. Не делай commit/push/deploy. Предлагай исправления в отчёте; реализацию выполняй только после отдельного разрешения.
2. Не выполняй разрушительные действия. Не запускай тесты, способные менять рабочую/production БД, пароль администратора, Telegram-аккаунты, кэш или пользовательские данные. Для integration/live-тестов используй только disposable DB или явно изолированное тестовое окружение.
3. Не обращайся к production-эндпоинтам, внешним аккаунтам или чужим системам без отдельного разрешения. Не запускай нагрузочные и DoS-тесты на живом сервисе.
4. **Не выводи секреты.** Не печатай значения `music.env`, ключи JWT/Fernet, пароли, Telegram session strings, access tokens, содержимое credential-файлов или полные строки с ними. В отчёте указывай только имя настройки, местоположение и безопасный статус, например `SECRET_KEY: найдено значение/похоже на placeholder`, без самого значения.
5. Не считай документацию, grep, TODO или теоретически возможный сценарий достаточным доказательством уязвимости. Найди фактический путь выполнения, предусловия и влияние. Каждую существенную находку подтверждай кодом, тестом, воспроизведением или явно обозначай как гипотезу.
6. Не объявляй проблему исправленной только потому, что в старом отчёте стоит «исправлено». Проверь актуальную реализацию и regression test. Аналогично, историческую находку не переноси в новые findings без перепроверки.
7. Не называй тесты пройденными, если не запускал их. Разделяй: **запущено и прошло**, **запущено и упало**, **не запускалось**, **заблокировано окружением**. Если падение связано с отсутствующей зависимостью или БД, отдели это от регрессии кода.
8. Сохраняй обратную совместимость API и данных как отдельный критерий: не предлагай «простое исправление», которое незаметно меняет контракты, формат стрима, Range, права доступа или поведение клиентов.
9. Не дублируй одну первопричину множеством находок. Связывай симптомные дефекты с корневой причиной.
10. Учитывай два возможных профиля развёртывания и оценивай их отдельно: **домашняя/LAN-сеть** и **публичный Internet-facing сервер**. Не называй сервис безопасным для публичного релиза, если проверена только локальная конфигурация.

## 5. Известные темы, которые обязательно перепроверить

Это **не заранее подтверждённые находки текущей версии**, а контрольный список по историческим заметкам:

- В аудите от **2026‑10‑19** публичный релиз имел статус `BLOCKED`: `SEC-001` — известный на тот момент слабый фиксированный пароль администратора (не цитируй и не выводи его значение в отчёте); `SEC-003` — исторический пароль PostgreSQL в Git history. Проверь текущие настройки, процедуру bootstrap, все используемые credentials, историю Git и подтверждение ротации. При этом не раскрывай сами секреты. Если модель публичного доступа сохраняется, слабый пароль без внешней сетевой изоляции — release blocker.
- `SEC-002` — ранее обнаруженная возможность блокировать веб-аккаунт через неудачную аутентификацию Subsonic — отмечена как исправленная. Проверь текущий код `subsonic_auth`/`subsonic_router` и regression test: unauthenticated ошибки Subsonic не должны блокировать учётную запись веб-пользователя; проверь также IP/account rate limit и возможность обхода лимитов.
- В том же отчёте были отмечены открытые для перепроверки темы: UDP-порт LAN Discovery **8211** (`SEC-005`), cookie `Secure`/HSTS при `COOKIE_SECURE=false` (`SEC-006`), определение IP и коллективная блокировка за reverse proxy при неверной настройке `TRUST_PROXY_HEADERS` (`SEC-007`).
- CORS для локального использования ранее сознательно оставляли без изменений; проверь `CORS_ALLOW_LAN`, `ALLOWED_ORIGINS`, credentials и реальную production-конфигурацию.
- Аудит производительности от **2026‑10‑21** описывает перенос блокирующих операций из event loop в threadpool/background tasks: синхронный Last.fm, обходы файлов/manifest-кэша обложек, проверки транскодинга и синхронные DB-операции. В документации нет живого замера после этих изменений. Проверь, что блокировки реально устранены и что код не получил race/cancellation/cleanup-регрессий.
- Старые UI-аудиты заявляют об исправлении найденных проблем, однако живая проверка на разных устройствах, iOS Safari, Android WebView/APK и выкладка некоторых изменений оставались открытыми. Проверь реализацию и отдели автоматические CSS/source guards от реальной визуальной верификации.
- В тестовой документации приведены исторические результаты разных дат и окружений. Не используй старое число passed как актуальный результат; запускай существующий набор там, где это безопасно.

## 6. Направления проверки

### A. Архитектура и качество кода

- Соблюдение слоёв router/controller → service → repository → model; прямой SQL в роутерах/сервисах без обоснования; смешение HTTP, бизнес-логики, SQL и Telegram-транспорта.
- God Objects, чрезмерно крупные модули/функции, циклические импорты, скрытые зависимости, дублирование логики, неиспользуемый код и мёртвые ветки.
- Типизация Python/TypeScript/JS, Pydantic-схемы, валидация на границах, корректная работа с `None`, исключениями, `Enum`/`Literal`, UTC/таймзонами и числовыми пределами.
- Единообразие контрактов API, HTTP status codes, заголовков, схем ответа, обработки неизвестных полей и обратной совместимости.
- Управление конфигурацией: fail-fast для обязательных значений, отсутствие небезопасных default, корректное разделение dev/test/production.
- Понятность владения состоянием и инвалидации кэшей; консистентность frontend stores и серверного состояния.
- Читаемость и сопровождаемость: соглашения имён, комментарии, logging, причины исключений, миграции схем и ADR.

### B. Бизнес-логика, async и надёжность

- Все ветвления, ранние return, циклы, фильтры, сортировки, пагинация, edge cases, пустые результаты, повторные запросы и конкурентные операции.
- Транзакционные границы, commit/rollback, partial updates, idempotency и уникальность; создание связанной сущности должно быть атомарным.
- Async event loop: блокирующий `urllib`, файловые обходы, `stat/resolve`, JSON parsing, SQLAlchemy sync calls, `ffprobe/ffmpeg`, CPU-bound код и KDF внутри `async def`. Проверяй реальный контекст запуска (threadpool/worker/background task), а не только наличие `async`.
- Правильное управление ресурсами: DB sessions/connections, async generators, SSE, Telegram clients, subprocesses, file handles, locks, semaphores, temporary files и object URLs.
- Отмена задач, клиентский disconnect, timeout, retry, backoff, shutdown/startup, повторное подключение Telegram, failover и `FloodWait`.
- Гонки при play/next/shuffle/pre-cache, смене трека и обновлении позиции, concurrent transcode jobs, cache eviction, дублирующих запросах и синхронизации каталога.
- Ошибки не должны бесшумно проглатываться без необходимости; логирование должно сохранять диагностические данные, но не секреты. UI не должен представлять сетевую/серверную ошибку как «ничего не найдено».
- Обработай корректность edge cases: длинные названия/пути, Unicode, oversized payload, пустые/повреждённые данные, повторные события, истечение токенов, неполные файлы и сбои внешних поставщиков.

### C. Производительность и масштабируемость

**Стриминг/транскодинг**

- Измерь TTFB/время первого аудиочанка отдельно от полного времени ответа; не трактуй `duration_ms` долгого stream-response как TTFB.
- Проверь `Range`/`206`, `Content-Range`, `Content-Length`, MIME, filename и total size для raw/cached MP3, encrypted и native-compatible файлов; корректность seek, EOF, upstream timeout и прерывания соединения.
- Проверь, не ждёт ли открытие альбома/папки завершения транскодинга всех треков; нет ли O(N²), полного перебора каталога cache manifests на каждый трек, повторного `get_status/get_result`, блокирующего ffprobe/JSON/file I/O.
- Проверь эффективность индекса manifest-кэша, TTL, атомарное создание/обновление, устаревшие/повреждённые записи, eviction и восстановление после рестарта.
- RAM cache: LRU, общий byte/item budget, защита от OOM, конкурентные загрузки одного трека, partial chunks, корректное удаление и освобождение памяти.
- Pre-cache: реальный shuffle-порядок, бюджет сети/памяти, ограничение параллелизма, отмена устаревших задач и запрет на принятие некорректного ответа вместо ожидаемого `206`.
- Telegram: число повторных скачиваний, корректность выбора аккаунта/failover, ограничения FloodWait и поведение при частичной выдаче.

**База данных и API**

- N+1, запросы в циклах, `SELECT *`, лишние `COUNT(*)`, отсутствие/неподходящие индексы, рекурсивные CTE и closure table, блокировки и долгие транзакции.
- Пагинация/лимиты на большие списки, эффективная фильтрация каталога и VFS, стоимость статистики PostgreSQL и запросов админки.
- Проверь сценарии с реалистичным объёмом данных: документация упоминает базу с тысячами альбомов и десятками тысяч треков, а также папку сборника на сотни треков.
- Проверь TTL и инвалидацию кэшей, single-flight, cache stampede, скрытое устаревание, размер объектов и консистентность данных после rename/delete/import.

**Frontend и клиентские ресурсы**

- Лишние рендеры, большие компоненты/чанки, лишние сетевые запросы, дублирование запросов между каталогом и плеером, polling и обработчики событий без cleanup.
- Производительность на слабых Android-устройствах, малой ширине экрана, больших каталогах и длинных очередях; виртуализация там, где она действительно нужна.
- IndexedDB/offline cache: LRU/TTL, race при одновременном кэшировании, размер Blob, освобождение Object URL, обновление метаданных, stale entries и корректное поведение при недостатке места.
- Производительность админки: повторные тяжёлые запросы, `pg_database_size()`, статистика таблиц, TTL memo и инвалидация после vacuum/analyze/reindex/restore.

**Метрики и методика**

- Используй воспроизводимые локальные/staging тесты, по возможности baseline vs after, realistic fixtures и несколько уровней concurrency.
- Где инструменты доступны, фиксируй p50/p95/p99, throughput, ошибки/timeouts, TTFB, event-loop lag, CPU/RAM, число/время SQL-запросов и размер кэшей.
- Не придумывай числовые результаты. Если измерить нельзя, укажи точный пробел и предложи команду/сценарий для следующего замера.

### D. Безопасность (AppSec/DevSecOps)

Оценивай по OWASP Top 10 / ASVS и практикам API security. Все эксплойтные проверки проводи только локально и на тестовых данных.

**Аутентификация и сессии**

- Argon2id: параметры, предел памяти/параллелизма, защита от resource exhaustion, миграция legacy bcrypt/старых хэшей, длинные UTF‑8 пароли и отсутствие silent password truncation.
- Login throttling, lockout, timing differences, enumeration, password change, bootstrap администратора и reset/recovery.
- JWT: допустимый алгоритм, `sub/exp/iat/jti/uid/tv`, типы и сроки claims, uid binding, token version, revoke/logout, server-side revocation, stream-token TTL/scope и поведение при clock skew.
- HttpOnly/SameSite/Secure cookies, double-submit CSRF на всех cookie-based mutations, CORS allowlist и `credentials`, TLS/HSTS, очистка cookie при logout.

**Авторизация API и злоупотребления**

- Инвентаризируй все маршруты, методы, dependency chain, роли/permissions, rate limits и body-size limits.
- IDOR/BOLA, privilege escalation, mass assignment, отсутствие auth на cover/media/admin/system endpoints, доступ к system/cluster status, self-service Subsonic token rotation и public shares.
- Сравни rate limits на `/api/*`, login, `/rest/*`, транскодинг/status/prefetch, импорт, client logs и тяжёлые admin maintenance actions. Учитывай несколько процессов/реплик и возможность обхода per-IP лимита.
- Проверь, что внешние ошибки не позволяют блокировать веб-учётную запись через Subsonic; повторяющийся запрос не должен давать дешёвый DoS или запускать неограниченные background jobs.

**Ввод, загрузки и данные**

- SQL injection, небезопасная динамическая сортировка/filtering, template/XSS, SSRF и DNS rebinding; запрет private/loopback/link-local/CGNAT/cloud metadata IP для remote cover fetch.
- Upload validation: magic bytes, размеры, MIME, SVG, multipart, decompression bombs, oversized JSON, path traversal, symlink/ZIP-slip и безопасные временные файлы.
- VFS SQL import: parse-only, не исполнять dump; allowlist таблиц/COPY, отклонять `COPY FROM PROGRAM`, binary dump и invalid UTF‑8, ограничить размер/TTL staging, не показывать credentials/session strings/raw SQL в preview/logs, безопасно обрабатывать конфликты и выполнять merge атомарно с rebuild closure table.
- Стриминг: scope токена, Range abuse, чтение чужих файлов/треков, authorization для share/Subsonic, race между проверкой прав и выдачей байтов.
- Telegram secrets: Fernet at-rest, fail-closed при неверном/отсутствующем `SESSION_SECRET`, отсутствие plaintext в БД/логах/бэкапах, корректный rotation/recovery plan.

**Секреты, логирование, мобильная и инфраструктурная безопасность**

- Secrets scan текущих файлов и Git history: не печатай найденные значения; проверь, была ли выполнена ротация исторических ключей/паролей, а не только удаление из текущей версии.
- Редакция query strings и credentials в logs, `?token=`, cookies, authorization headers, client logs, tracebacks и сообщения внешних процессов.
- Security headers/CSP без `unsafe-inline` в `script-src`, `nosniff`, frame policy, Referrer/Permissions Policy, HSTS при HTTPS.
- Android/Capacitor: release `usesCleartextTraffic=false`, нет wildcard `allowNavigation`, правильные permissions, безопасный remote origin, хранение токенов/аудио в локальном кэше и поведение APK/WebView.
- Docker/host: non-root, `no-new-privileges`, `cap_drop: ALL`, доступность портов, PostgreSQL bind только к необходимому интерфейсу, `.env`/`.secrets` вне Git и build context, корректные volume permissions, backup/restore и health checks.
- Reverse proxy: `X-Forwarded-For` доверяется только от контролируемого proxy, который перезаписывает заголовки; проверь rate limiting и lockout при нескольких клиентах за одним proxy.

### E. UI/UX, доступность и мобильные сценарии

Проверяй не только CSS и source guards, но и реальные пользовательские сценарии там, где браузер/device доступен.

- Все состояния: loading, empty, success, error, offline, unauthorized, rate-limited/429, stale data, retry и partial failure. Различай «нет данных» и «не удалось загрузить».
- Плеер: play/pause/next/prev, shuffle/repeat/queue, seek, volume, смена трека, транскодинг, failover, ошибка потока, history/resume, повторные нажатия и восстановление сессии.
- Не сбрасывай playback/queue только из-за временного сетевого сбоя `checkAuth`; проверяй согласованность между `App.jsx`, `authStore`, `playerStore`, `<audio>` и Media Session.
- Каталог и админка: большие списки, поиск, сортировка, inline rename, редактирование обложек, массовые действия, удаление, VFS sync/import, прогресс и отказ частичной операции.
- Accessibility: семантические кнопки/ссылки, keyboard-only, корректный Space/Enter, `focus-visible`, focus trap/return в модалках, Escape, ARIA labels, dialog/progressbar semantics, live regions, heading structure, контраст, screen-reader names и alt-текст.
- Touch/mobile: разумные touch targets (цель около 44×44 CSS px), отсутствие hover-only controls, отсутствие горизонтального overflow и перекрытий, safe-area insets, dynamic viewport units (`dvh`), portrait/landscape и низкие экраны.
- Breakpoints и проверка минимум на ширинах 320/360/380/640/900 px; отдельно проверь мини-плеер, полноэкранный плеер, громкость, очередь, тексты песен, track menus, toasts, offline banner, topbar и stacking contexts/z-index.
- PWA/Android: Media Session на lock screen/авто, reconnect и офлайн, кэшированный/некэшированный трек, Blob URL cleanup, фоновые задачи и нативный APK/WebView.
- Предотвращай двойные действия: pending/disabled состояния, confirm для destructive actions, сохранение фокуса, ясные сообщения и отсутствие полной перезагрузки страницы там, где она сбрасывает плеер.
- Производительность UX: виртуализация/пагинация больших списков, скелетоны/индикаторы, отсутствие скачков layout и видимый прогресс долгих операций.

### F. Тесты, зависимости и готовность эксплуатации

- Изучи существующий тестовый стек и CI, затем безопасно запусти доступные проверки: backend unit/integration, frontend Node tests, production build, linters/type checks, dependency/security scans и Android build/test, если соответствующие инструменты присутствуют.
- Не запускай live-DB suite без понимания фикстур: документация предупреждает, что часть тестов меняет тестовые записи и пароль `admin`. Используй изолированную БД/snapshot. Если тестовый runner требует `pytest-asyncio` или иной пакет, зафиксируй это как проблему окружения/CI, а не как доказанную регрессию.
- Проверь покрытие критических потоков регрессионными тестами: auth/JWT/CSRF/rate-limit; Range/seek/encrypted size/failover; cancellation/timeout/early EOF; transcode states и manifest cache; VFS import rollback; permissions/IDOR; cache invalidation; admin bulk operations; frontend playback and offline flows; keyboard/mobile layout.
- Проверь pinned dependencies, lockfiles, известные CVE, обновляемость, повторяемость сборки, конфигурацию CI и отсутствие drift между source и `frontend/dist`.
- Проверь operational readiness: backup/restore, health/liveness/deep checks, structured logs, мониторинг 401/403/429/5xx, FloodWait/failover, cache hit/miss, transcode queue, event-loop lag и DB pool.

## 7. Методика подтверждения находок

Для каждой находки:

1. Дай стабильный ID, например `CODE-001`, `PERF-001`, `SEC-001`, `UX-001`, `TEST-001`.
2. Укажи категорию, severity и приоритет исправления. Используй шкалу:
   - **P0 / Critical:** непосредственный критический риск безопасности/потери данных или безусловный блокер публичного релиза.
   - **P1 / High:** серьёзная уязвимость, вероятный outage, повреждение данных или критический пользовательский сценарий.
   - **P2 / Medium:** значимый дефект с ограниченными условиями/обходным путём.
   - **P3 / Low:** небольшая проблема качества, UX или сопровождения.
3. Отдельно укажи confidence (`высокая/средняя/низкая`) и статус (`подтверждена`, `историческая — больше не воспроизводится`, `гипотеза`, `заблокирована окружением`).
4. Покажи точные `path:line` и функцию/компонент; коротко цитируй только необходимый безопасный фрагмент.
5. Опиши: сценарий/предусловия → фактическое поведение → ожидаемое поведение → impact → вероятную root cause.
6. Приведи воспроизводимые шаги или тест, а для безопасности — безопасный локальный PoC без воздействия на production.
7. Предложи минимальное исправление и более устойчивый вариант, если они различаются; назови нужный regression test.
8. Зафиксируй затронутые API/данные/клиенты и возможный риск обратной совместимости.
9. Если найдено исправление в текущей ветке, проверь его эффект и тест на повторное появление.

Не присваивай `Critical` только из-за названия CWE/OWASP; учитывай эксплуатируемость, доступность маршрута, привилегии, влияние и контекст LAN vs Internet. Но не занижай пароль администратора/секреты или достижимый unauthenticated DoS.

## 8. Формат итогового отчёта

Сформируй отчёт на русском языке в Markdown со следующей структурой.

### 1. Executive summary

- Общий вердикт: `PASS`, `CONDITIONAL` или `BLOCKED` — отдельно для LAN и public Internet.
- 3–7 важнейших выводов без маркетинговых формулировок.
- Количество подтверждённых P0/P1/P2/P3; отдельно — гипотезы и ограничения окружения.
- Условия, без которых нельзя рекомендовать публичный релиз.

### 2. Scope и достоверность

- Что просмотрено: подсистемы, файлы/каталоги, commit/branch.
- Какие команды реально запускались и итог каждого запуска.
- Что не проверено и почему: живая БД, Telegram, настоящий Android/iOS, браузерные сценарии, нагрузка, Git history и т. п.

### 3. Матрица покрытия

Таблица по областям `Architecture/Code`, `Business Logic`, `Async/Resources`, `Performance`, `Database`, `Security`, `API`, `UI/UX`, `Accessibility`, `Mobile/PWA`, `Tests/CI`, `Infra/Ops` со статусом проверки, найденными ID и ограничениями.

### 4. Реестр находок

Таблица: `ID | Priority | Severity | Area | Finding | Evidence (path:line) | Confidence | Status | Release blocker?`.

Затем развернутые карточки только для реальных находок в порядке риска.

### 5. Производительность

Для каждой проверенной критической операции: сценарий и размер тестовых данных, baseline, результат, p50/p95/p99 (если замерены), concurrency, CPU/RAM/SQL/event-loop lag при наличии, узкое место, рекомендации. Явно разделяй TTFB и время завершения stream-response. Не заполняй метрики догадками.

### 6. UI/UX и доступность

Таблица `Сценарий | Устройство/viewport | Шаги | Фактический результат | Ожидаемый результат | Severity | Evidence/скриншот/тест`. Раздели автоматические проверки, браузерную проверку и реальный device smoke.

### 7. Тесты и качество сигналов

Список команд, точный результат (`passed/failed/skipped`, exit code), основные причины падений и отличие дефекта продукта от проблемы тестовой среды. Укажи, какие рисковые сценарии не покрыты тестами.

### 8. План исправлений

- **P0 — до любого публичного доступа.**
- **P1 — до релиза/широкого использования.**
- **P2 — ближайший инженерный цикл.**
- **P3 — плановое улучшение.**

Для каждой задачи укажи ожидаемый эффект, зависимости, ориентировочную сложность (`S/M/L`, не часы), нужные regression tests и критерий приёмки.

### 9. Release gate

Явная таблица условий `Условие | Статус | Доказательство | Остаточный риск`. Статус `PASS` допускается только при наличии фактического доказательства. Если не удалось проверить критичный пункт, используй `UNKNOWN/CONDITIONAL`, а не `PASS`.

### 10. Документация к обновлению

Перечисли Obsidian-заметки, которые противоречат коду или устарели, с точным предлагаемым изменением. Не переписывай документацию без разрешения.

## 9. Критерии завершения аудита

Аудит считается завершённым, когда:

- изучено актуальное дерево репозитория, конфигурация, тесты и релевантная документация;
- основные пользовательские и security-critical потоки прослежены от UI/API до данных/внешнего сервиса;
- подтверждённые проблемы отделены от гипотез и исторических находок;
- выполнены все безопасные и доступные статические/автоматические проверки;
- ограничения окружения зафиксированы явно;
- у каждой значимой находки есть evidence, риск, reproduce steps, fix direction и критерий регрессионной проверки;
- вынесен честный release gate отдельно для LAN и Internet-facing сценариев;
- прикладной код и данные остались неизменными.

Начни с инвентаризации проекта и сопоставления актуального кода с Obsidian. Затем проходи направления A–F последовательно, сохраняя находки в реестре. Не ограничивайся выдачей общего чек-листа: сформируй выводы по конкретному коду и подтверждённым результатам.
