0. Резюме решения

Цель: sideload-APK с личным музыкальным плеером на базе существующего React-PWA, с фоновым и lock-screen воспроизведением на Android 14+ (API 34).

Выбранный путь: Capacitor (Android) в remote-режиме — WebView загружает развёрнутый T-Music по адресу сервера (server.url), а не бандлит dist/ локально.

Почему remote-режим, а не бандл / TWA

  • frontend/src/api/client.js работает на BASE_URL='' + HttpOnly-cookie SameSite=Lax + CSRF double-submit. Локальная схема Capacitor (https://localhost) делает сервер кросс-ориджиновым → cookie не отправляются, auth ломается. Переделка на Bearer — лишний фронтенд-рефакторинг (сервер его поддерживает: backend/app/api/dependencies.py, CSRF для Bearer отключён в backend/app/core/csrf.py, stream-токены ?token= уже есть в stream.js). В remote-режиме origin = реальный сервер → вся существующая JS-логика работает без изменений.
  • TWA/Bubblewrap отпадает: требует публичный HTTPS + верификацию assetlinks.json, а сервер может быть LAN-ным.
  • Фоновое воспроизведение в WebView нативно появилось именно на Android 14: androidx.webkit MediaSessionManagerCompat (мост navigator.mediaSession WebView → системная MediaSession) раскрывается на Android 13/14 WebView; поэтому «порт на 14+» содержателен, а не формален.

ФАЗА 0

Prerequisites (среда разработки + сервер)

≈ 0.5 дня · без этого фаза 2 невозможна

  1. Установить Android-окружение (сегодня на машине НЕТ SDK/adb/gradle; Java 17 ✓, Node 22 ✓):
    • Android Studio (или command-line tools) → SDK Platform 34/35 + Build-Tools, принятие лицензий sdkmanager --licenses;
    • env: ANDROID_HOME=%LOCALAPPDATA%\Android\Sdk; adb в PATH.
  2. HTTPS для экземпляра T-Music — обязательное условие: navigator.mediaSession и service worker доступны только в secure context. Варианты (выбрать один, ⚑):
    • домен + Caddy/Nginx + Let's Encrypt (правильно, если сервер доступен извне);
    • tailscale serve (автоматический TLS для личного доступа, без публичного DNS);
    • mkcert: локальный CA + .test-домен, корневой сертификат установить в хранилище Android (Настройки → Безопасность → доверенные учётные данные).
    • Проверить COOKIE_SECURE: на HTTPS ставить true в music.env (+ HSTS уже отдаётся main.py).
  3. На телефоне обновить Android System WebView и включить режим разработчика.
  4. Выход фазы: сервер отвечает https://… с валидным сертификатом; adb devices видит телефон.
ФАЗА 1

Каркас оболочки (mobile/ в корне репозитория)

≈ 0.5 дня

Отдельная папка, чтобы не смешивать npm-зависимости фронта и обёртки.

mobile/
├── package.json            # @capacitor/core, @capacitor/cli, @capacitor/android
├── capacitor.config.ts     # см. ниже
├── www/index.html          # заглушка-загрузчик (remote-режим грузит сервер;
│                           #  офлайн-экран нужен только при недоступном сервере)
└── android/                # `npx cap add android` — нативный проект (патчится в Фазе 2)

capacitor.config.ts:

{
  appId: 'app.tmusic.mobile',          // ⚑ финальное имя пакета выбрать раз и навсегда
  appName: 'T-Music',
  webDir: 'www',
  android: {
    allowMixedContent: 0,               // никакого http-контента на https-странице
  },
  server: {
    url: 'https://<tmusic-host>',       // адрес из Фазы 0
    hostname: 'tmusic.app',
    allowNavigation: ['<tmusic-host>'],
  },
}
  • Команды: npm init -y && npm i @capacitor/core @capacitor/cli @capacitor/android && npx cap init … && npx cap add android && npx cap sync.
  • Иконки: npm i -D @capacitor/assets → сгенерировать из frontend/public/icon.svg adaptive icon + splash (npx capacitor-assets generate --android).
Выход: npx cap open android собирает дебаг-APK, который открывает T-Music в WebView; вход по логину работает, cookie переживают перезапуск.
ФАЗА 2

Нативный слой: background playback + media session

≈ 1–2 дня · самый трудоёмкий этап · все правки — в mobile/android/app/src/main/

1. AndroidManifest.xml — permissions и service

<uses-permission android:name="android.permission.FOREGROUND_SERVICE"/>
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK"/>
<uses-permission android:name="android.permission.POST_NOTIFICATIONS"/>
<uses-permission android:name="android.permission.WAKE_LOCK"/>
...
<service android:name=".MediaPlaybackService"
         android:foregroundServiceType="mediaPlayback"
         android:exported="false"/>

Плюс android:allowBackup="false" (не выносить cookie-хранилище WebView в бэкапы).

2. MainActivity.kt (наследник BridgeActivity из Capacitor)

  • settings.mediaPlaybackRequiresUserGesture = false;
  • НЕ вызывать webView.onPause() при уходе в background (переопределить lifecycle-хуки Capacitor-моста так, чтобы аудио продолжалось);
  • при старте — запрос POST_NOTIFICATIONS (runtime, API 33+);
  • обработка onNewIntent для тапов по notification-действиям (play/pause/next/prev — dispatch в JS, см. п.4).

3. MediaPlaybackService.kt — foreground-service mediaPlayback

  • startForeground() с типом mediaPlayback и persistent-уведомлением: обложка (URL из MediaMetadata уже приходит из JS-слоя), title/artist, действия Play/Pause/Next/Previous, MediaStyle;
  • запуск только из активного UI (в API 34 действуют FGS-ограничения; сценарий «запустить музыку, потом свернуть» их удовлетворяет) — service стартует при первом play() и останавливается при pause()/stop();
  • onTaskRemoved: оставить воспроизведение до конца трека, затем stopSelf (⚑ политику «swipe-to-kill» — решить на тестах).

4. Мост WebView ↔ система (ключевое)

  • androidx.webkit:webkit:1.12+, MediaSessionManagerCompat.from(context).setDelegate(ServiceDelegate(this)), где ServiceDelegate:
  • onActive()/onInactive() → start/stopForeground service;
  • onPlaybackStateChanged / onMetadataChanged / onPositionStateChanged → обновление уведомления и lock-screen (обложки, кнопки, прогресс — всё уже публикуется из frontend/src/services/mediaSession.js: metadata, positionState, action handlers);
  • системные команды (кнопки уведомления/BT-гарнитуры) Android 14 delegate принимает и транслирует сам в navigator.mediaSession.setActionHandler внутри WebView — повторной прокладки в JS не нужно; проверить на тестах, при глюках — костыль через evaluateJavascript;
  • build.gradle: implementation "androidx.webkit:webkit:1.12.0", androidx.media при необходимости.

5. Gradle

minSdk 34, targetSdk 34, compileSdk 35 — в mobile/android/app/build.gradle; подпись release — см. Фазу 4.

Выход: с телефона: play → экран выключен → музыка играет; на lock-screen обложка/прогресс/кнопки; с BT-наушников next/pause; при остановке воспроизведения service останавливается.
ФАЗА 3

Минимальные правки во фронтенде

≈ 0.5 дня · web-код остаётся единым, адаптации — под флагом окружения

  1. frontend/src/services/nativeBridge.js (новый, ~20 строк): детект оболочки (navigator.userAgent содержит TMusicApp/) → экспортировать const IS_NATIVE.
  2. frontend/src/store/playerStore.js + App.jsx:38–56 (watchdogs / armGlobalResume / visibilitychange-replay): при IS_NATIVE не включать ensureWatchdog (interval) и global-resume слушателей — в WebView с FGS и mediaPlaybackRequiresUserGesture=false они создают риск двойного play/pause-мигания и фоновой нагрузки. Обычные ended-обработчики очереди оставить.
  3. frontend/src/api/stream.js: getStreamUrl(fileId) оставить — cookie same-origin работает (remote-режим = origin сервера), токен-режим не нужен.
  4. App.jsx: скрыть UI-бейдж «PWA update / install prompt» при IS_NATIVE; статус-бар: theme-color из manifest уже #141210 — синхронизировать цвет статус-бара Android (native, MainActivity.setStatusBarColor).
  5. sw.js не трогаем: в WebView он регистрируется так же, даёт shell-cache; для remote-режима безвреден.
  6. Проверить index.html/App.jsx на beforeinstallprompt — ничего не ломать (в WebView события не срабатывают).
Выход: регрессия в обычном Chrome на том же URL: lock-screen, перемотка, очередь — без изменений; APK-путь без watchdog-мигания.
ФАЗА 4

Сборка, подпись, дистрибуция (sideload)

≈ 0.5 дня

  1. Keystore один раз: keytool -genkeypair -alias tmusic -keystore tmusic-release.jks (пароли — в mobile/android/keystore.properties; .gitignore: mobile/keystore.properties, *.jks).
  2. build.gradle → signingConfigs.release из keystore.properties; assembleRelease с minify (R8) от Capacitor — держать keep androidx.webkit.** в proguard-rules.
  3. Билд-скрипт scripts/build_android_apk.ps1: cd frontend && npm run build → cd ../mobile && npx cap sync → cd android && .\gradlew assembleRelease → артефакт app-release.apk.
  4. Установка на телефон: adb install -r (или файлом через «неизвестные источники»). applicationId/package стабильны → переустановка поверх без потери сессии в cookie jar WebView.
Выход: подписанный release-APK, ставится и работает на Android 14.

РАЗДЕЛ 8

Вне объёма / будущие расширения

  • Нативный Kotlin/Compose-клиент — не делается в этом плане.
  • Портирование сервера (FastAPI/PostgreSQL/Telegram) на устройство — отдельный проект.
  • Play Store (assetlinks, App Bundle, требование 16 KB page size — для sideload неактуально).
  • iOS-сборка того же wrapper (Capacitor её покрывает почти бесплатно, но вне рамок «Android 14+»).
  • Экран настройки server URL внутри APK (появится вместе с режимом local bundle).
